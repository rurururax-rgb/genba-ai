- 状態: **仕様の合意待ち**。コードの実装・migration の作成と適用・本番 DB への書き込みはしていない

  1. `vendor_invoice_documents` を新しく作り、請求書 1 枚を 1 件として扱う（本番への migration の適用は未承認）

## 1. 目的と、守る約束

現場の請求書は 1 枚に複数の材料・工事が並び、見積のいろいろな工種・項目に対応する。今は 1 枚を台帳の 1 項目にしか登録できない。
これを「明細を読み取る → 登録先の候補を出す → 人が確認する → 複数の台帳項目にまとめて登録する」にする。

| # | 約束 | どこで守るか |
|---|---|---|
| 1 | 自動マッチングは候補を出すだけ。未確認・あいまいな候補を自動で承認しない | 画面（承認の状態）・API（承認されていない行は送らない）・RPC（振り分けの合計の照合） |
| 2 | 金額を AI に推測・計算させない | 読み取りの指示・決まった計算だけで作る候補・人の確認 |
| 3 | 振り分けの合計 = 確定した税抜請求額。合わなければ登録しない | RPC（1 円単位） |
| 4 | 同じ請求書を二重に計上しない（画像の圧縮・旧画面・新画面の間でも） | 重複検出の 4 段階（§6）・RPC 内の advisory lock |
| 5 | 1 枚の請求書の登録は、全部成功するか全部失敗するか | RPC 1 回 = 1 トランザクション |
| 6 | 既存の見積項目・台帳項目を勝手に作らない・変えない（実績原価の再集計を除く） | RPC は請求書の表と実績原価だけを書く |
| 7 | 実績原価の集計・重複防止・再送の安全・RLS を壊さない | 既存の制約・P1-3 のトリガー・P1-4 の権限をそのまま使う |
| 8 | 請求実績のある台帳項目が、見積の同期や削除で合計から消えない | §8（アプリと DB の両方） |

## 3. 全体の流れ

```
① 読み取り（今の画面）   原本と読み取り結果を見比べ、税抜の請求額を確定 →「原本で確認しました」
② 振り分け（新しい画面）  明細ごとに登録先の候補を出す → 一覧でまとめて承認・あいまいな行だけ選ぶ
③ 確認して登録           項目ごとの合計を確認 →「一括登録」（RPC 1 回）
```

- 「全部を 1 つの項目に登録」も残す（今と同じ使い方。中身は振り分け 1 行の一括登録）。
- 一括登録のあとは、台帳に請求書ごとのまとまりとして表示し、「請求書ごと削除」で取り消せる。

## 4. データモデル（明細と振り分けの対応をどう持つか）

### 4.1 比較

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A: JSONB だけ | 請求書の表に明細と振り分け（台帳項目 ID・金額）を JSONB で持つ。台帳への計上は別に `cost_ledger_invoices` | 表が 1 つで済む | JSON の中の台帳項目 ID には外部キーが効かない（他社・別案件・削除済みを DB で止められない）。項目ごとの集計が JSON 頼みで、計上の行とずれうる |
| B: 別の表を 2 つ | `vendor_invoice_lines`（明細）と `vendor_invoice_allocations`（振り分け）。計上は `cost_ledger_invoices` | 外部キーで完全に守れる。検索しやすい | 表・RLS・RPC が増え、計上の行と振り分けの行が二重になる（ずれの元） |
| **C: 推奨（MVP）** | 請求書の表に**明細の写し**を JSONB で持つ（印字どおり・あとから変えない）。**振り分け 1 件 = `cost_ledger_invoices` の 1 行**で、`document_id` と `document_line_no` を持たせる | 明細 → 台帳項目の対応が既存の外部キー（台帳項目）と新しい外部キー（請求書）で守られる。計上の行がそのまま振り分けの記録なので、ずれない。新しい表は 1 つ | 明細の写しの中身は外部キーで守れない（行番号の範囲は RPC で確かめる）。台帳の請求書一覧で行が増える（請求書ごとにまとめて表示する） |

**採用: 案 C。** 振り分けは計上そのものなので、「振り分けの記録」と「実績原価の元」を同じ行にする。別に持つと、ずれたときにどちらが正しいか分からなくなるため。
明細の写しは監査用（何が印字されていたか）で、集計には使わない。

### 4.3 `cost_ledger_invoices` の変更（列の追加だけ）

- `document_id uuid NULL`、`document_line_no int NULL` を追加する。
- 複合外部キー `(document_id, project_id)` → `vendor_invoice_documents(id, project_id)`、ON DELETE RESTRICT。
- `source` に `'ocr_document'` を追加する（CHECK の置き換え）。
  - `source='ocr_document'` ⇔ `document_id IS NOT NULL`（CHECK）
  - その行は `document_sha256` と `idempotency_key` を NULL にする（既存の一意制約 ① ② と衝突させない。キーは請求書の表が持つ）
- 1 つの明細を複数の項目に分けたときは、同じ `document_line_no` の行が複数できる。複数の明細を 1 項目にまとめたときは、同じ台帳項目に行が複数できる（台帳では請求書ごとにまとめて表示する）。
- 既存の行は変えない（新しい列は NULL のまま）。

## 5. 金額の扱い

### 5.1 振り分ける金額は税抜

実績原価は税抜で集計する（KI-004）。消費税と源泉徴収は振り分けない。

### 5.2 明細の種類（`kind`）と初期値

| kind | 例 | 振り分け | 振り分け額の初期値 |
|---|---|---|---|
| `item` | 材料・工事 | する | 明細の金額が**税抜で印字**されていればその金額。税込・不明なら**空欄** |
| `discount` | 値引き・出精値引き | する（マイナス） | 印字の金額（マイナス）。登録先は空欄（人が選ぶ） |
| `rounding` | 端数調整・端数値引き | する（マイナス・プラス） | 同上 |
| `withholding` | 源泉所得税 | **しない** | — （請求書の表の `withholding_amount` に記録するだけ） |
| `other` | 前回繰越・相殺など | **しない**（登録できない。原本で確認して手で直す） | — |

- 明細の金額が税抜か税込かは、原本の税区分（外税・内税）と印字から決める。分からなければ `unknown` とし、税抜の初期値は出さない。
- 値引き・端数を振り分けたあと、**どの台帳項目も実績原価がマイナスにならない**こと（RPC で確かめる）。
- 金額は 1 円単位の整数で、0 ではないこと。

### 5.3 税込で印字された明細の税抜候補（人が操作する補助）

**使える条件（すべて満たすときだけボタンを出す）**
1. 税率が 1 つ（混在していない。税率が印字されている）
2. 原本の金額が整合している（PR #48 の照合が「OK」で、税込合計 − 消費税額 = 確定した税抜請求額）
3. 値引き・端数・源泉徴収・その他の増減がない
4. 明細がすべて `item` で税込。明細の合計 = 印字された税込合計（1 円単位）
5. 明細の全行を読み取れている（行数が一致。§10）

**計算（決まった計算だけ。AI は使わない）**
- 各行の候補 = 切り捨て(行の税込額 × 確定した税抜請求額 ÷ 税込合計)
- 端数の差（確定した税抜請求額 − 候補の合計）は、税込額がいちばん大きい行に足す（同じ額なら上の行）
- 画面に出すもの: 計算式、各行の候補、**端数の調整額と調整した行**、「この候補を使う」ボタン
- ボタンを押しても承認にはならない。各行は「要確認」のまま、人が一覧で承認する

この補助は PR 5（任意）で入れる。それまでは、税込の明細は空欄で、人が入力するか「全部を 1 つの項目に登録」を使う。

### 5.4 照合（登録できる条件）

| 照合 | 種類 | 内容 |
|---|---|---|
| 振り分けの合計 = 確定した税抜請求額 | **必須（RPC）** | 1 円でも違えば登録しない。画面に「残り ¥Z」を常に出す |
| 明細の合計と原本の小計（または税込合計）の一致 | 警告 | 読み落とし・読み違いの手がかり。合わなければ明細の行を直すよう案内する |
| 明細の行数 = 原本の行数 | 警告 | §10 |
| 各台帳項目の実績原価 ≥ 0 | **必須（RPC）** | 値引きの付け先の誤りを止める |

## 6. 二重計上を防ぐ（画像の圧縮・旧画面・新画面）

| 段階 | 判定 | 強さ | 補足 |
|---|---|---|---|
| L1 | 同じ案件に、送られた画像の SHA-256 が同じもの | **拒否** | 今と同じ（縮小後の画像のハッシュ） |
| L2 | 同じ案件に、縮小前の元ファイルの SHA-256 が同じもの | **拒否** | 縮小の結果が端末で違っても、同じ写真ファイルなら同じ値になる。ブラウザが計算する値なので信用はしない（すり抜けは L3・L4 で拾う） |
| L3 | 同じ案件・同じ業者・同じ請求書番号（表記ゆれを揃えたキー） | **拒否** | 撮り直した写真・別の端末でも効く。請求書番号が無い請求書には効かない |
| L4 | 同じ業者・請求日・金額（確定した税抜、または税込合計）が近いもの | **確認を求める** | 今の「似ている請求書」と同じ。人が「別の請求書です」と確認すれば登録できる |

- **L1〜L4 は、新しい表と、旧画面で登録した `cost_ledger_invoices`（`source='ocr'`）の両方を見る。** 旧画面の行は税込で入っている可能性があるため（KI-004）、L4 は税抜と税込の両方の金額で比べる。
- **競合を防ぐ:** 一括登録の RPC と旧画面の登録 RPC の両方で、同じ advisory lock を取る。鍵は「案件 + 業者のキー + 請求書番号のキー」と「案件 + 画像のハッシュ」で、RPC の中でロックしてから確認と登録をする。
- **旧画面からの登録の停止:** PR 4 で画面の OCR 登録をすべて新しい流れに切り替える（1 項目だけでも振り分け 1 行の一括登録にする）。旧 RPC の `source='ocr'` での登録は、新しい表と重なれば拒否する確認を足す。手動登録（`manual`）は今のまま。
- **別の案件への登録:** 同じ請求書を別の案件に登録することは、正当な場合もある（1 枚に 2 現場分）。会社全体で L2・L3 が一致したら警告だけ出す（拒否しない）。

## 7. 一括登録の RPC（全部成功か全部失敗か）

`public.vendor_invoice_register(p_project_id uuid, p_document jsonb, p_allocations jsonb, p_idempotency_key uuid) RETURNS jsonb`

1. `auth.uid()` が無ければ CL401。入力の形・件数（振り分けは 200 行まで）・金額（整数・0 以外）を確かめる（CL400）。
2. 案件を読み、会社を決める（リクエストから会社を受け取らない）。案件が未削除で、呼び出した利用者がその会社のメンバーであること（CL404）。
3. **再送:** 同じ `idempotency_key` の請求書があれば、同じ内容かを確かめて保存済みの結果を返す（違う内容なら CL409）。
4. **advisory lock**（§6 の鍵）→ L1〜L3 の重複を確かめる（CL409 + どの段階か）。L4 は `p_document.confirm_similar` が無ければ CL409 で候補を返す。
5. **対象の台帳項目を `id` の順に `FOR UPDATE` でロックする**（デッドロックを防ぐ）。すべてが同じ案件・同じ会社・未削除であること（CL404）。
6. 照合: 振り分けの合計 = `confirmed_excl_tax`、行番号が明細の範囲内、`withholding` と `other` の明細には振り分けない（CL400 / CL422）。
7. 請求書の表に 1 行と、振り分けの行（`cost_ledger_invoices`、`source='ocr_document'`）を登録する。
8. 触れた台帳項目ごとに実績原価を再集計する（P1-3 を満たす）。いずれかが負になれば CL422 で全体を取り消す。
9. 請求書の ID・項目ごとの新しい実績原価・件数を返す。

`public.vendor_invoice_delete(p_document_id uuid)`: 自社のメンバーであることを確かめ、関係する台帳項目を `id` の順にロックし、振り分けの行と請求書を削除して再集計する。

**既存 RPC への変更（小さなガードだけ）**
- `cost_ledger_invoice_update`・`cost_ledger_invoice_delete`: `document_id` のある行は CL409（請求書ごとに扱う）。
- `cost_ledger_invoice_insert`: `source='ocr'` のときに §6 の advisory lock を取り、新しい表と L1・L3 が重なれば CL409。

**セキュリティ**
- 新しい RPC はすべて SECURITY DEFINER、`SET search_path = ''`、`SET lock_timeout = '5s'`。RLS に頼らず、本文で所属会社を確かめる。
- `REVOKE ALL ... FROM PUBLIC, anon, service_role`、`GRANT EXECUTE ... TO authenticated`（P1-4 と同じ）。
- 新しい表は anon・authenticated に SELECT だけ（RLS つき）。書き込み権限なし。
- 隔離 DB でのテスト: 他社・別案件・削除済みの項目と案件・未ログイン・権限（anon は EXECUTE 不可）・直接の INSERT・UPDATE が拒否されること・同時実行（同じ請求書を 2 つの接続から → 1 件だけ）・再送・L1〜L3・合計の不一致・負の実績原価・P1-3・既存 RPC のガード・RLS の前後比較。

## 8. 見積同期・削除で実績原価が消える問題（先に直す）

### 8.1 今の `/api/cost-ledger/sync` の問題

1. 見積で削除された行（`estimate_items.deleted_at` あり）に対応する台帳項目を、**請求書・実績原価・予算があっても論理削除する**。案件の合計（`GET /api/cost-ledger`）から、その実績原価が消える。
2. 論理削除された項目の請求書は、RPC が「削除済みの項目」として扱うため、**編集も削除もできなくなる**（CL404）。
3. 見積行を戻したり追加し直したりすると、新しい台帳項目が作られる（元の項目は戻らない）。請求書は消えたほうに残る。
4. 更新・追加・論理削除の結果を確かめていない（失敗しても成功として件数を返す）。1 回の同期が途中まで反映されうる。
5. 同期と請求書の登録が同時に起きると、登録した直後の項目が論理削除されうる（同期は読んでから書くため、ロックの対象外）。
6. 手動の削除 `DELETE /api/cost-ledger/[id]` も、請求書があっても論理削除する。

物理削除された見積行は、PR-4b の外部キー（ON DELETE SET NULL）で `estimate_item_id` が NULL になり、同期の対象から外れる（台帳項目は残る）。消えるのは論理削除の場合。

### 8.2 対策

| 段階 | 対策 | DB |
|---|---|---|
| PR S（アプリ） | 同期: 請求書・`actual_cost`・`budget_cost`・`completion_cost` のどれかがある項目は論理削除せず、「見積から削除済み（請求あり）」として残し、件数を返す。画面に表示する。更新・追加・削除のエラーを確かめ、失敗を報告する | なし |
| PR S（アプリ） | 手動の削除: 請求書がある項目は 409（「先に請求書を削除してください」）。実績原価・予算があれば確認を出す | なし |
| PR 4（DB） | トリガー `cost_ledger_items_guard_soft_delete`: 請求書がある項目の `deleted_at` を NULL 以外にする UPDATE を拒否する（P1-3 と同じ考え方。直接の書き込みや同時実行でも止める）。物理削除は外部キーで止まる | migration |
| 既存データ | PR 0 の F 節で件数を確かめる。**戻すかどうかは人が決める**（このシリーズでは既存データを変えない） | 読み取りのみ |

## 9. 自動マッチング（候補を出すだけ）

- 候補の範囲: 同じ案件の**未削除の台帳項目**だけ。台帳にない見積項目は「台帳に未登録」として出し、選べない（同期を案内する）。台帳項目も見積項目も作らない。
- 点数（プログラムで計算。AI は使わない）:
  - 品名の類似度（pg_trgm）。比べる相手は、台帳項目名と、紐付いた見積項目の名前・説明
  - 型番の一致（英数字とハイフンのまとまりが完全に一致する）
  - 業者名の一致（台帳項目・見積項目の業者名）
  - 工種名、単位の一致、数量の一致
- 1 行あたり最大 3 件の候補を出す。
- **「確実」の条件（すべて満たす）:** 1 位の点数が高い（初期値 0.8 以上）、2 位との差が大きい（0.2 以上）、明細が `item`、振り分け額の初期値がある（税抜で印字）。閾値は実データで調整する。
- それ以外は「要確認」。候補が無ければ「未割当」。

## 10. 明細の全行読み取り（20 行の制限への対応）

- 1 回目で請求書の情報と、明細の行数・最初の 40 行を読む。残りは「41〜80 行目」のように範囲を指定して、同じ画像で読み足す（1 回あたり出力 4,096 トークン以内。短い配列形式 `[no, name, spec, qty, unit, amount]`）。
- 1 回ごとに途中終了を検出する（PR #48 と同じ）。1 回でも失敗すれば、その範囲を「読み取れなかった」と表示し、行を手で追加・編集できるようにする。
- 完全かどうかの確認: 行数が原本の行数と一致、行番号の抜け・重複なし、明細の合計と小計の照合（§5.4）。
- 上限: 1 枚 200 行・AI の呼び出し 5 回まで。超えたら「全部を 1 つの項目に登録」を案内する。関数の最長実行時間（今は 60 秒）は範囲ごとに 1 リクエストにして超えないようにする（画面から順に呼ぶ）。

## 11. 画面（現場の人が迷わない形）

```
┌ 請求書：QA設備 / 2026-10-01 / 税抜 ¥100,000 ─────── 残り ¥0 ┐
│ ✅ 確実（12 行・¥82,000）              [まとめて承認]          │
│   給湯器 XX-123   ¥80,000 → 給湯器交換工事        (変更)      │
│   …                                                          │
│ ⚠ 要確認（3 行・¥18,000）  1 行ずつ登録先を選ぶ               │
│   配管部材一式    ¥20,000 → [候補1 ▼]  [分ける]               │
│   出精値引き      −¥2,000 → [未選択 ▼]                        │
│ ⛔ 未割当（0 行）                                              │
└───────────────────────── [全部を1つの項目に] [確認して登録] ┘
```

- 状態は 3 つだけ: **確実**（まとめて承認できる）・**要確認**（1 行ずつ選ぶ）・**未割当**。
- 「確実」のグループには「まとめて承認」ボタンを 1 つだけ置く。押すまで承認されない。個別に外すこともできる。
- 「要確認」「未割当」の行は、登録先を選んで承認するまで登録できない。**自動では承認しない**。
- 金額や登録先を変えた行は承認が外れる（PR #43 の確認チェックと同じ考え方）。
- 「分ける」: 1 行を複数の登録先に分ける。分けた額の合計が元の行と一致しないと承認できない。
- 「確認して登録」が押せる条件: 残りが ¥0、すべての行が承認済み、§5.4 の必須の照合を満たす。押すと、項目ごとの合計の一覧を出し、もう一度確認してから登録する。
- スマホでは 1 行 1 カード。入力途中の内容はブラウザに残す（台帳の同期をしに行って戻っても消えない）。
- メモは人が入力したときだけ保存する（自動では入れない。QA-A で決まった方針）。

## 12. 切り戻し（データを残したまま）

登録が始まったあとは、表を消すと計上の行が宙に浮くため、**表の削除による切り戻しはしない**。

| 段階 | 方法 | データ |
|---|---|---|
| R0 | 会社ごとの機能の出し分けを OFF（新しい画面を出さない。今の 1 項目の登録に戻す） | そのまま。登録済みの実績原価は正しく残る |
| R1 | 新しい RPC の EXECUTE を取り消す（新しい登録・削除を止める）。台帳の表示は残す | そのまま |
| R2 | 既存 RPC のガードを外す（1 行ずつ編集・削除できるように戻す）。請求書の表は残す | そのまま（請求書の合計と振り分けの行がずれうるので、人の判断で） |
| R3（最後の手段） | 請求書の表を退避用の表へ写してから、振り分けの行の `document_id` を外し、`source` を `manual` に変える。**データの変更なので人の承認が必要** | 実績原価は変わらない（行と金額は残る） |

各段階の SQL は、PR 4 で apply・rollback・verify と一緒に用意し、隔離 DB で「R0〜R2 のあとも実績原価と請求書の合計が変わらない」ことを確かめる。

## 14. 主なリスク

1. **本番の `cost_ledger_invoices` の定義が想定と違う。** PR 0 の B 節で確かめる。違えば PR 3 の設計を直す。
2. **既存データで、論理削除済みの項目に請求書がある。** その実績原価はすでに案件の合計から消えている。PR 0 の F 節で件数を出し、戻すかどうかは人が決める。
3. **重複検出のすり抜け。** 請求書番号が無く、撮り直した写真で、金額や日付も違って読まれると、L1〜L4 のどれにも当たらない。確認画面で業者名・日付・金額を必ず見せ、「似ている請求書」を一覧で出す。
4. **候補の誤りを「まとめて承認」してしまう。** 「確実」の条件を厳しくし、まとめて承認する前に金額と登録先の一覧を出す。閾値は実データで調整する。
5. **明細の全行読み取りの費用と時間。** 行数に応じて AI の呼び出しが増える。上限（200 行・5 回）を超えたら「全部を 1 つの項目に」を案内する。
6. **振り分けを直すには「請求書ごと削除 → 登録し直す」が必要。** 現場の手間になる。部分修正は PR 5 で検討する。
7. **旧画面との並行期間。** PR 4 で切り替えるまでは、旧画面からの OCR 登録も残る。advisory lock と L1・L3 の確認で、両方からの二重登録を防ぐ。
8. **ロールバック R3 はデータを変える。** 人の承認なしには実行しない。
