# 見積OCRの原本照合UI — 1画面とデュアルモニターの段階導入

## 目的
見積エディタでは既存の「明細をドラッグして任意の位置に入れ、登録成功後に候補が減る」を維持し、請求書OCRのように原本と金額を見比べてから取り込む。

## 第1段階（このPR）
- 同じ取り込みパネル内に、元画像のプレビューと候補カードを表示
- 明細の「原本を見る」で取り込み元画像を表示
- ページ切替、原本のズーム、全画面に近い拡大表示
- 画像はブラウザのblob URLのまま参照し、DB・Storageには保存しない
- 追加・drag/drop、確認フラグ、API、原価・売価計算は変更しない
- PR #52（OCR安全対策）をベースとする積み上げPR

## 第2段階（別PRで設計・検証してから実装）
### 構成
- 左ウィンドウ: 見積エディタ。保存先の案件ID・グループID・挿入位置を指定。
- 右ウィンドウ: 原本プレビューと候補。確認・修正・追加操作に集中。
- UIの配置だけ変える。OCR・要確認の判定・登録は共通コードを使い、別々の実装を作らない。
- ブラウザをまたぐドラッグ&ドロップは前提にしない。選択済み挿入先への「追加」操作を優先。

### 先に満たすべき安全条件
1. 同じ案件にログイン済みであることを両ウィンドウで確認する。broadcastされた内容を認可情報として信用しない。
2. 単一の所有者が候補・確認状態を管理する。操作順序を示すIDと応答で双方の画面が同期する。
3. 登録を行う前に、送信中・送信済みIDを確認。メッセージの重送・再送・並行操作が起きても二重登録しない。ブラウザ内の重複対策だけでDB全体の重複防止を保証したとは言わない。
4. 通信断・ポップアップブロック・片方のウィンドウを閉じた場合に、状態を失わず元の1画面に戻れるようにする。
5. 内容を変えたら確認フラグを取り消し、元画像と候補の対応が崩れないことを確認する。
6. 候補画像は必要な範囲で端末内だけに保持する。ウィンドウ間で画像を渡す場合、セキュリティとメモリ量を評価してから方式を決める。
7. DBの変更が必要なら別PRにし、実装前に理由と安全対策をレビューする。

### 検証項目
- 1画面 / 2画面切替、原本切替、ズーム、候補の修正、警告確認、個別/一括追加、任意位置への挿入
- 2ウィンドウ同時操作・同じボタンの連打・読み取り中の閉じる/再読み込み・通信断
- ファイル名が同じ別画像、複数ページ、誤警告、HEIC、巨大写真
- 見積に登録した値、原価×掛率、社内メモの保存、既存の請求書OCRへの影響
